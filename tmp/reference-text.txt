Abstract— Denial-of-Service Attacks Dispersed (DDoS) attacks put cybersecurity on risk by flooding systems with too many queries, making services unavailable. Traditional lightweight detection techniques are not feasible deployments since they are based on expensive machine learning or hardware technologies. This paper outlines an extensible, real-time DDoS detection system that logs, detects, and visualises abnormalities in web traffic using Node.js, WebSockets, and Chart.js. A Node.js backend, a web hosted on Google Cloud Storage (GCS), and dynamically updated in real-time monitoring dashboard make up the system. A threshold-based detection system will alert users immediately through WebSockets within Requests Per Second (RPS) exceed 5. The ability to recognize high request rates maintaining low-latency realtime updates was confirmed through testing. Without requiring sophisticated infrastructure, this solution is affordable, scalable, and effective DDoS detection technique that is appropriate for small to medium-sized online operations.
Keywords— Cybersecurity, DDoS Detection, Node.js, Real-Time Monitoring, WebSockets

I] INTRODUCTION  
In the constantly changing environment of cyberspace, firms across the globe now put a premium for safe and secure access to online services. An unprecedented dependence on interlinked systems has followed from the digital age, making their availability and integrity critical to business operations, communication and fundamental services. Cyber-attacks have also became more complex by the exponential increase in usage of the internet because of advances in computer technology. Alas, this increase in connectivity has also led to an increase in level and complexity of cyberattacks, which has created serious problems for businesses of every type.
Among these are distributed denial of service (DDoS) attacks are among the most intrusive. These attacks attempt to exhaust system resources and successfully prevent authorized users from utilizing services by striking the target server or network with a large number of requests from a variety of sources. To achieve this, DDoS attacks overburden the target's legitimate processing capabilities requests, thus robbing the target consumers of service.
DDoS attacks are not just a technical nuisances; they can make significant contributions to an organization's operations, finances, and reputation. These attacks can cause everything from brief service interruptions to protracted outages, which can lead to monetary losses from missed sales, lower productivity, and harm to a brand's reputation. Websites that rely on internet infrastructure,  such  as  government  and e-commerce sites, are vulnerable. Due to the extensive use of online platforms, DDoS assaults could target almost any organisation that depends on the internet.
Attackers commonly produce traffic floods that are difficult to detect or effectively filter by using "botnets," or networks of compromised devices. Botnets are made up of several compromised devices that are controlled remotely by an attacker. These devices are frequently spread across many geographic regions. Because botnets are dispersed, it can be challenging to discern between malicious attack activity and genuine user traffic because the latter comes from a variety of sources. As these attacks are spread, they are particularly difficult to rebut.
Some of the latest DDoS attacks that typically evade conventional defences such as firewalls and intrusion detection systems are volumetric and application-layer attacks. Application-layer attacks target particular defects in apps to disrupt their functionality, whereas volumetric attacks focus on bandwidth utilization by inundating the target with a lot of traffic. Since these advanced attack methods usually circumvent traditional security measures, increasingly sophisticated detection and mitigation efforts are required. With changing attack methods, there is the increasing need for intelligent real-time detection systems that can process massive amounts of network traffic.
Instead of relying on advanced ML models, this system optimizes for light and lean method for detecting early DDOS attacks without the need for advanced AI/ML algorithms. III.I] Algorithm: Threshold-Based DDoS Detection
The threshold-based DDoS detection system algorithm, which is optimized for real-time network traffic analysis, is its fundamental building block. This algorithm's main function is to identify suspicious network traffic patterns characteristic of a DDoS attack and to send out alerts when such patterns are detected.
The algorithm operates in the following steps:
1.	Traffic Logging and Monitoring: The system logs significant information regarding each request while constant monitoring of incoming network traffic. The source IP address, the method of the request (e.g., GET, POST), the exact timing of the request being some examples of such information. This detailed traffic data logging is needed for later analysis and anomaly detection.
2.	Threshold Comparison and Real-Time Analysis: A threshold method is used to examine the real-time recorded traffic information. This includes computing the rate of requests, which is typically expressed as Requests Per Second (RPS), and to compare it to a preconceived cut-off point.
3.	Rolling Count Mechanism: The algorithm keeps an ongoing count of the requests that come from each IP session or address within an indicated period of time (e.g., one second in attempting to properly place abrupt traffic spikes. The system is able to track current request activity and detect potentially harmful floods due to this rolling tally.
4.	Anomaly Detection and Alerting: The system marks an IP address as a suspect if the number of requests placed from that IP address within a time period within the time specified threshold. Warning that implies a potential DDoS assault is triggered by this.
5.	Response activities: The system has the capability to initiate a sequence of response actions when it identifies a possible DDoS attack. These steps could consist of:
5.1.	Blocking the source of the traffic: blocking the IP address which was discovered to be attack source, either momentarily or indefinitely.
5.2.	Rate-limiting the source of traffic: limiting how many of the suspicious IP requests address are allowed in small quantities of time.
5.3.	Capturing the source of the traffic: maintaining complete accounts of the suspicious activities to be investigated in due course.
Due to its simplicity to use and efficiency, the threshold-based detection technique was utilized facilitating quick deployment of the system and low overhead. Although machine learning is not used in in the current implementation, modular design allows with ease the inclusion of other advanced detection technologies if necessary

III.V] Algorithm for DDoS Detection: Detailed Steps
In order to detect possible DDoS assaults, the system uses a threshold-based detection approach which is mostly monitoring the Requests Per Second (RPS). The next step-by-step detailed process includes the algorithm:
1.	Log Requests: The system records comprehensive information about each request sent to the target website by a user (or a simulated user in the testing environment). At the very least, this log entry contains the request's source IP address, the date that indicates when it was received, and maybe other pertinent information like the resource that was requested (URL), the request type (GET, POST, etc.), and user agent characteristics.
2.	Determine RPS: The Requests Per Second (RPS) are continuously determined by the Node.js backend. The time span across which this computation is carried out is set to one second in this implementation. The quantity of requests received during that one-second period is tallied for every distinct IP address. This gives a measure of the request rate coming from each source in real time.
3.	Compare RPS Against Threshold: Next, each IP address's computed RPS is contrasted with a predetermined threshold. The maximum allowable number of requests per second from a single IP address under typical operating circumstances is represented by this barrier.
3.1.	Normal Traffic: Traffic from an IP address is regarded as being within the normal range if its computed RPS is less than or equal to the threshold (in this case, RPS ≤ 5). The system keeps tracking the traffic and no alert is raised.
3.2.	DDoS assault Indication: A possible DDoS assault is indicated if an IP addresses RPS above the cutoff point (RPS > 5). A prominent feature of many DDoS assaults, in which attackers try to overload the server with traffic, is this abrupt spike in requests from a single source.
4.	Trigger WebSocket Alert: The Node.js backend instantly initiates a DDoS alert when it detects a possible DDoS assault (i.e., when RPS > 5). All WebSocket clients that are connected receive this notice; these are usually the dashboards that network administrators use for real-time monitoring. The alert message contains details about the attack's time, severity, and attacking IP address. 
5.	Visualize Data: The WebSockets-updated real-time monitoring dashboard shows any warnings that have been generated and dynamically visualizes the incoming traffic data. Administrators may easily spot irregularities and comprehend the nature of the assault by using Chart.js to generate graphs and charts that display traffic trends over time.
This threshold-based technique offers a straightforward but efficient method for real-time detection of high-frequency DDoS attacks.
III.VI] WebSocket-Based Alert System: Real-Time Communication
The Node.js server and the frontend monitoring dashboard can communicate in real time thanks to the system's use of WebSockets. This is essential for sending out notifications on time and giving managers a real-time picture of network activity.
This is how the WebSocket-based alert system works:
1.	Real-Time Communication: All active clients, or monitoring dashboards, are connected to the Node.js server via persistent, open WebSocket connections. In contrast to the request-response nature of classic HTTP, WebSockets provide continuous, bidirectional data flow.
2.	Instant Data Push: The server instantly notifies all WebSocket clients connected to it whenever it logs a new request or when a DDoS alarm is triggered. The clients no longer need to "poll" the server for updates on a regular basis, which would add latency and increase server load, thanks to this "push" technique.
3.	Dynamic Alerts and Dashboard Updates: The server broadcasts a DDoS alert message to all dashboards that are linked when the RPS over the predetermined threshold (5 in this example), which suggests a possible DDoS attack. The dashboard dynamically modifies its display to reflect the attack after receiving this alarm. This could include:
3.1.	Highlighting on the traffic graphs the unusual traffic patterns.
3.2.	Notifying the administrator by displaying an alert banner or message.
3.3.	Supplying information about the attack, including the time of the assault and the IP address of the source.
Administrators have the capability to react promptly and efficiently to DDoS attacks since WebSockets provide for the alerts to be delivered to them with no delay.
III.VII] Performance Considerations: Optimization for Real-Time Efficiency
Performance is a priority on the agenda in the design of DDoS detection system with the goal of low latency operation, optimal use of resources, and scalability to support different traffic loads. These performance targets are established by a number of significant design decisions and improvements
1.	File-Based Logging: It uses file-based logging to preserve incoming traffic data rather than a conventional database system. A basic file text traffic.log holds all of the traffic data. As it reduces cost and latency in database queries, connections, and transactions, that technique produces significant performance benefit during high-frequency request scenarios.
2.	Lightweight Detection Logic: Threshold-based RPS computation is the foundation for the essential detection logic, that is intentionally lightweight. It stays away from resource-intensive algorithms or sophisticated computations like those in in machine learning-based methods. This guarantees short detection time and reduces the server processing load.
3.	WebSocket-Based Real-Time Updates: One of the most important performance optimizations is the use of WebSockets for communication the server and the dashboard. Regular polling, with the dashboard sending periodically requests to the server to see if there are updates, is no longer required because of WebSockets. This lessens latency and adds responsiveness by minimizing server load and network traffic.
4.	Effective Front-End Visualization: Because of its effectiveness and cheap resource usage, Chart.js is utilized for front-end visualization. The purpose of It is used to generate dynamic charts and graphs smoothly with the least possible memory usage possible. This makes the realtime traffic graphs in the dashboard be updated on a regular basis without using too much system power.
Combining these design options allows the system to manage high traffic efficiently without compromising real-time detection ability and supporting a user-friendly monitoring interface.

V] FUTURE SCOPE
V.I]	Adaptive Detection Algorithms: Intelligent Thresholding
Although the existing system's static threshold of 5 Requests Per Second (RPS) works well in many typical attack scenarios, it might not be the best choice for traffic patterns that are dynamic or unpredictable. A set threshold may result in either missed attacks during naturally high traffic periods or, on the other hand, a higher number of false positives during traffic surges unrelated to malicious activity in environments with changing legitimate traffic levels.
Adaptive machine learning (ML) techniques that can dynamically learn and adapt to the protected system's baseline traffic behaviour may be incorporated into future improvements. By examining past network traffic data, these algorithms would be able to spot reoccurring patterns and track changes in acceptable user behaviour. The system may automatically modify the detection thresholds on the fly by continuously monitoring and learning from previous traffic, increasing its sensitivity to real anomalies while lowering the possibility of false alarms. This adaptive strategy would maintain the system's lightweight nature by increasing the system's detection accuracy for both low-and-slow and high-volume (volumetric) DDoS attacks without adding a substantial computing expense.
V.II]	Real-Time	Traffic	Classification: Differentiating Malicious Intent
Request rate is the only sign of possible malicious behaviour in the current system. As a result, it is unable to distinguish between criminal high-traffic events—like coordinated botnet attacks—and legal high-traffic events—like viral marketing campaigns, massive file downloads started by a large number of users, or abrupt increases in interest brought on by trending news.
The system's capacity to distinguish between attack traffic and legitimate user behaviour would be greatly improved by the addition of real-time traffic classification modules. This might entail looking at more than simply the request rate while analysing traffic, like:
1.	Analysing the order and trends of requests made during certain user sessions is known as session behaviour. Unlike typical user browsing patterns, malicious sessions may display repetitive or odd request sequences.
2.	Examining the distribution of source IP addresses is known as source diversity. While normal traffic spikes are usually characterised by a wider dispersion of sources, an attack may be indicated by a highly concentrated volume of requests coming from a small number of IP addresses.
3.	Request Type and Frequency: Examining the different kinds of requests (such as GET and POST) and how frequently they are made for particular resources. Malicious activity may be indicated by unusual request types or unusually high frequency of requests for particular, resource-intensive endpoints.
4.	Payload examination (Superficial): A lightweight system may not be able to handle the resource demands of deep packet inspection, however anomalies suggestive of specific attack types may be found through superficial examination of request headers or payload sizes.
The system might considerably lower false positives and react more precisely and successfully to real DDoS attacks by integrating real-time information on the type and characteristics of the traffic. More sophisticated automated mitigation techniques might potentially be influenced by this more detailed knowledge of traffic.
V.III] Traffic Filtering and Rate-Limiting: Active Defence Mechanisms
Although detection and warning are the current system's main priorities, adding active reaction mechanisms will greatly improve its defensive capabilities. Later editions might include rate-limits as well as real-time traffic screening that automatically reply when suspicious behaviour is detected. For example, the system can run the following automatically when it notes an IP address beyond the defined threshold:
1.	Temporary block: For a specific amount of time, temporarily stop all incoming traffic to the attack IP address that has been determined.
2.	Put request throttling into practice to slow quelling the attack by inserting delays into requests from the suspicious IP address.
3.	Use IP-based rate-limiting with a time period for which one can make requests from dubious IP address are permitted.
By limiting the range of the attack, these preventative measures would not only assist in protecting server resources and also provide that legitimate users could continue to access the service even throughout the course of the attack.
Web	Application	Firewall	(WAF) Integration: Coordinated Security Response
Enhancing the system's compatibility with modern Web Application Firewalls (WAFs) is another exciting trajectory of future development. The detection system would automatically apply preconfigured WAF mitigation rules on detection of a DDoS attack pattern by generating communication channels with WAFs. For instance, the system automatically tells the WAF to do the following when it finds a hostile IP address or a specific attack signature:
4.	Block the IP that has been recognized.
5.	To restrict traffic from zones that are determined to attack sites, employ geo-blocking.
6.	Utilize challenge-response strategies, such as CAPTCHAs, to distinguish between automated bots and actual users.
By decreasing the level of human intervention by network administrators and greatly speeding up reaction times, this smooth defensive cycle— detection and subsequent automatic protection— would minimize the impact of DDoS attacks.
V.IV] Large-Network Scalability: Adapting to High-Traffic Environments
Small and medium-sized online business companies, e.g., local facilities or services with restricted access, are the primary target of the existing system architecture. Architectural changes would be required to scale the system to meet the demands of high-traffic settings, including cloud-based infrastructures or enterprise-level networks. This might entail:
1.	By integrating load balancers, incoming traffic may be split among several instances of the detection system, guaranteeing peak performance and avoiding bottlenecks.
2.	Distributed detection agent deployment: To improve detection accuracy and lessen the strain on a central server, lightweight detection agents are being implemented across a variety of network nodes to monitor traffic closer to its source.
3.	Putting horizontal scaling into practice for processing and logging services: allowing additional instances to be added as traffic volume rises, allowing the system to expand its logging and processing capabilities.
4.	Using an architecture based on microservices: increasing flexibility and robustness by dividing the system into smaller, separate services that can be independently deployed, scaled, and managed.
With the help of these architectural improvements, the system would be able to continue operating efficiently and effectively even when large-scale networks experience significant traffic loads.
V.V]	Enhancements to Visualization: Deeper Analytical Insights
Future improvements could greatly increase operator understanding and decision-making skills by integrating more complex analytics and visualisation approaches, even though the existing monitoring dashboard only offers basic real-time traffic visualisation. Possible enhancements consist of:
1.	Multi-layered visualisations: Showing several traffic data elements at once, including heat maps superimposed on geography maps to show the origin of traffic, giving possible attacks a spatial context.
2.	Historical trend graphs: Showing past traffic patterns next to current data might assist administrators in spotting anomalies and comprehending long-term patterns.
3.	IP frequency bar charts are a useful tool for rapidly identifying the main causes of traffic spikes by visualising the frequency of requests from various IP addresses.
4.	Interactive indications of anomalies: Directly highlighting identified anomalies on the traffic graphs makes it simple for administrators to link triggered alarms to visual patterns. With their use of such advanced visualisation techniques, administrators would be better off comprehend the attack surface, spot minute irregularities, and more active and targeted security measures.

VI] CONCLUSION
This essay traces the development and use of a light-weight real-time system for DDoS detection meant to effectively monitor web traffic and prompt identification of attacks. The system efficiently detects suspicious behavior when traffic is over a set to 5 Requests Per Second (RPS) with a threshold-based detection method. The system is built using WebSockets for real-time dialog, Chart.js for dynamic front-end visualization, Node.js for backend processing. This supports instant alert delivery with minimal delay. System responsiveness, dependability, and resource efficiency— particularly for small- to medium-sized applications—were rigorously tested and validated performed in real traffic conditions and simulated attack scenarios.
While the system is superb, its adaptability in more complicated and volatile traffic situations might be limited by its rigid threshold model. The accuracy of detection would greatly be boosted by such as adaptive detection algorithms, which react to traffic baselines and anomalies while time. Improved defense against repetitive attacks would also be provided by encompassing mitigation methods such as automatic filtering, IP-based rate limiting, or response triggers. Moreover, amelioration due to advanced traffic analysis tools also decrease false positives and improve the capacity to differentiate between harmful and benign traffic spikes.
Finally, the project presents a feasible, cost-effective, and scalable DDoS solution detection in real time. For small businesses, educational facilities, or local services in search of protection from basic denial-of service attacks, its ease of deployment and operation simplicity make it an excellent choice. The system has the capability of becoming a holistic security solution that may defend against more advanced and widespread cyber-attacks as subsequent editions include flexibility and mitigation.
